# @open3dj/agent

The agent panel of `open3dj view`: a person types a request in the viewer page, and a model works on the project with the five Open3DJ tools. The design is RFC 0001 (`rfcs/0001-agent-panel.md`, issue #31).

**Status: ready, not wired.** Engine A runs a turn (plan step B4), so `PACKAGE_STATUS` is `"ready"`. The records of step B5 are here (approval cards, the budget ledger and the egress log); the session that keeps them, with the event log and replay, comes next. Nothing in `open3dj view` calls the package yet: the routes and flags come in B6.

The package never loads the kernel (it runs inside the `open3dj view` process) and has no third-party dependency: only `@open3dj/mcp`, `@open3dj/schemas` and Node's `fetch` and `node:crypto`.

## What is here

| File | Export | What it does |
|---|---|---|
| `src/types.ts` | `Engine`, `TurnRequest`, `AgentEventBody`, ... | The shared contract. An `Engine` (`api` or `cli`) has `status()`, `turn(req)`, `reset()` and `close()`; `turn()` never throws and ends with a reason (`end_turn`, `max_rounds`, `max_tokens`, `context_window`, `refusal`, `stopped`, `budget`, `timeout` or `error`). The events, keyed by `kind`, are what the page shows; the session (step B5) will add `seq`, `ts` and `turn`. |
| `src/api-tools.ts` | `apiTools()` | The five tools as Messages API entries `{name, description, input_schema}`, in the fixed order run, inspect, render, export, docs, made from `TOOL_DEFINITIONS` in `@open3dj/mcp`. Each input schema loses `$schema`, `$id`, `title` and any top-level `anyOf`, `oneOf` or `allOf`; run's `anyOf` (script or ops) becomes one sentence of its description, and any other top-level combinator throws, so a schema change cannot drop a rule unnoticed. `project` is removed from run, inspect, render and export. Every call returns new objects with the same bytes, so prompt caching can reuse the tools part of each request. |
| | `withProject(name, input, project)` | Puts the pinned project back into a tool input. A project the model sends anyway is accepted only when it is the pinned path or the pinned folder's name; anything else is a `PATH_REFUSED` result (a tool result, not a throw) that names only the folder. |
| `src/results.ts` | `toApiContent(callResult)` | Maps an MCP `CallResult` (from `callTool()` in `@open3dj/mcp`) to the `content` and `is_error` of a Messages API `tool_result` block. Text stays text, cut at 64 KiB in all with a note that says how much was shown. One PNG becomes a base64 image block; more images are left out with a count. An SVG resource becomes a note naming the file. Images the API would refuse are left out with a reason: not PNG, over 10 MB base64, or over 3,000 px on a side. |
| | `redactText(text)` | Removes anything shaped like an Anthropic API key and home folder paths, value by value for JSON text. |
| `src/prompt.ts` | `systemPrompt()` | One system text that is the same bytes on every call: a short preamble for the viewer page, the MCP server's `INSTRUCTIONS`, and the body of `skills/open3dj/SKILL.md` without its YAML front matter. |
| `src/sse.ts` | `SseParser`, `readSse()` | A server-sent-events parser over bytes, after the WHATWG rules: chunks may split a line or a UTF-8 character anywhere; LF, CRLF and CR end lines; comments are skipped; data lines join with a newline; an unfinished event at the end is dropped; one event is capped at 32 MiB. |
| `src/stream.ts` | `MessageAccumulator` | Turns the stream events (`message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`, `ping`, `error`) into the final assistant message, its usage, `stop_reason` and `stop_details`. Text, tool_use, thinking (with its signature) and redacted_thinking blocks are kept as sent. A tool input is parsed strictly at its block's end; input that is not a JSON object keeps its raw text and reason, and the block's input becomes `{}`. An unknown block or delta type is the error "unsupported response block <type>; update Open3DJ", never a guess. Unknown event types are ignored, as the API's versioning allows. `outputReported` says whether a `message_delta` gave the reply's output count; until then the output in its usage is only `message_start`'s placeholder. |
| `src/client.ts` | `createApiClient({apiKey, baseUrl?, fetch?, sleep?})` | Speaks the Messages API over `fetch` with `anthropic-version: 2026-10-21`. The key lives only in the function's closure and goes only into the `x-api-key` header. 429, 5xx and network errors are retried twice, honouring `retry-after` (seconds or an HTTP date, capped at 60 s; otherwise 1 s, then 2 s), and Stop cuts a wait short. 401 becomes "the API key was refused" and a 404 on `/v1/messages` "unknown model". A redirect is never followed (it would carry the key, and for 307 and 308 the body, to another address): any 3xx answer is an error and is not retried. Every message it makes goes through `redact()`, which removes the key by value and any `sk-ant-` run. The base URL must be https, or http on 127.0.0.1 for tests. |
| `src/models.ts` | `listModels(client)` | `GET /v1/models`, page by page with `after_id` until `has_more` is false, newest first as the API lists them: `{id, display_name, max_tokens?, max_input_tokens?}`. Ids outside the documented form are left out. Open3DJ never names a model. |
| `src/api-engine.ts` | `createApiEngine({client, handlers, project, systemPrompt?, now?})` | Engine A, below. |
| `src/approval.ts` | `Approvals`, `buildPayload()` | The egress approval cards, below. |
| `src/ledger.ts` | `BudgetLedger` | The session budget: input and output token caps set once from the CLI options (defaults 4,000,000 and 200,000), `add()`, `remaining()` (never below 0) and `snapshot()`. Every input token counts against the input cap, cached or not (`input`, `cache_read` and `cache_write`), because each was sent. One request may pass the cap; the next one does not start. Nothing can raise a cap. |
| `src/egress-log.ts` | `EgressLog` | An append-only JSON Lines file at the path it is given, made owner-only (folder 0700, file 0600, also when the file already exists). One record per approval decision and one per request: time, approval id and payload hash, engine, host, model, and for a request its bytes, attempts, usage and outcome. Each record is checked against `packages/schemas/json/egress-record.schema.json`, which has no field for free text, and anything shaped like a key is refused, so the prompt text and keys never reach the file. |
| `src/fake-messages-api.testing.ts` | (tests only) | A fake Messages API on 127.0.0.1. It scripts a reply per request, records each request's method, path, headers and body, streams SSE in 7-byte chunks, and can answer 401, 404, 429 with `retry-after`, 500, a mid-stream error event, `max_tokens` and `refusal`, or keep a stream open until the client goes away. |

## Engine A, one turn

- **Requests.** `POST /v1/messages` with `model`, `max_tokens`, `system`, `tools`, `messages`, a top-level `cache_control` and `stream: true`. It never sends `thinking`, `effort`, `temperature`, `top_p` or `top_k`. The model comes from the person's pick in the model list; with none, the turn ends at once.
- **Caching.** The one system block carries `cache_control: {type: "ephemeral"}`, which covers the tools before it; the top-level `cache_control` is the automatic breakpoint for the growing conversation. Tools and system are built once and are the same bytes in every request.
- **Tools.** Each tool is sent with `eager_input_streaming: true`, so the engine validates: an input that is not a JSON object, or fails the tool's schema (`tool-<name>-input`) once the project is pinned, gets an `is_error` result and does not run. Calls run one after the other through `callTool()` with `withProject()`, and all results of one reply go back in one user message. A run that leaves out `base_rev` gets the last revision this conversation saw, with a notice, so a person's save in between gives `REV_CONFLICT` instead of a silent overwrite. `onRevision()` is called after a run that returns a revision.
- **History.** Append-only, and kept across turns until `reset()`. A reply joins it only once it is complete. Thinking blocks go back unchanged. Every tool_use gets a tool_result, also when it does not run, so the next request is always valid. A prompt that was never sent (for example when the budget is used up) is not added, and neither is one that got no reply (an error, Stop or the time limit before the first reply was complete), so sending it again sends it once; once a round has a reply, the prompt and the model's work stay. A refusal leaves the history as it was before the prompt (below). Each cut goes back to a prefix, so the cache and thinking signatures stay valid.
- **Limits.** A round is one request. When the reply of the last round (`maxRounds`) asks for tools, they get "not run: this prompt's limit of N tool rounds was reached" and the turn ends `max_rounds`. `maxOutputTokens` must be at least 1,024 (`MIN_OUTPUT_TOKENS`); a lower limit ends the turn at once as invalid limits, never as a used-up budget. `max_tokens` is the smaller of `maxOutputTokens` and the output budget left; under 1,024 the turn ends `budget`, as it does when no input budget is left. A reply that ends before the API reports its output tokens (Stop, the time limit, an error event or a dropped stream) counts the request's whole `max_tokens`, with a notice: the streamed part is billed and hidden thinking may have used more, so only that keeps the output budget a cap. The time limit (`timeoutMs`) covers the whole turn through `AbortSignal.any` with the person's Stop, and the injected clock is checked between steps.
- **Stop reasons.** `tool_use` runs the calls. `max_tokens` with an open tool call answers it with a request for a shorter call, sends one more request, and then ends `max_tokens`. `model_context_window_exceeded` (the whole conversation filled the context window, not the output limit) keeps the reply, closes any cut-off call with "not run", and ends `context_window` with a message that asks for New conversation. `refusal` follows the API's guidance to discard the partial reply and not go on from the declined turn: nothing of the reply runs, its shown text gets a `discard` event, and the prompt with every tool round of this prompt is left out of the history, so a rephrased prompt starts from the conversation before it. Revisions stay in the project, and the `base_rev` the engine fills in goes back to the last revision the remaining conversation saw, so a later run reports them as `REV_CONFLICT` instead of overwriting them. If the conversation had seen no revision before the declined prompt, there is no earlier head to fill in: a run without `base_rev` then gets a `NOT_RUN` result asking the model to inspect the project first, until the conversation sees a revision again. A notice names `stop_details.category`, and the turn ends `refusal`. `pause_turn` sends the next request. `end_turn` and `stop_sequence` end the turn. Anything else is an "unsupported stop reason" error.
- **Stop.** During a stream, the partial reply is dropped (a `discard` event) and never added. During a tool run, the agent's jobs are cancelled (`handlers.shutdown()`), the call gets "stopped by the person while this call ran." with its own result if it settles within 5 s, and every later call gets "not run: stopped by the person.".
- **Events.** `text` as it streams (the end of the text is held back while it could be the start of a key), `discard`, `tool_call` (an input preview of at most 32 KiB and the input's size), `tool_result` (status, revision, error code and one line, for example "r_0012 ok, 5 of 5 definitions valid"), `usage` per request (the request, this engine's total and what the budget has left) and `notice`. `prompt`, `status` and `turn_end` are left to the session (step B5). `onRequest()` reports each request's size, attempts, usage and outcome for the egress log (step B5), never its text.
- **The key** never appears in an event, a returned message or a request report: text, previews, summaries, notices and errors go through the client's `redact()`.

## The egress approval

The session (next) sends nothing off the machine until the person approves a card it made itself (RFC 0001, ahead of the S5 approval service). The card's payload names the engine, who pays, the host, the model (or null when Claude Code names it only once it starts), the project folder's name, the prompt, the conversation the engine resends (messages and bytes), Open3DJ's instructions and tool list (count, bytes and a short sha256), the limits, the budget left, and an input estimate of all those bytes divided by 4, labelled as an estimate.

- `payload_hash` is sha256 of the payload as canonical JSON with sorted keys. Approving or denying needs it, so what the person approves is what is sent.
- A card expires 10 minutes after it was made (the clock is injectable). An expired card answers `expired`, every time.
- A decision is final: a second decision on the same card is refused with `ALREADY_DECIDED`.
- Scopes: `prompt` covers one prompt. `session` ("don't ask again until this viewer stops") is allowed only for `computer`, this computer's own page, never for a paired device (`device:<id>`), and only when the card offers it; a prompt from a device gets a card with `prompt` only.

## Tests

All offline: the fake Messages API on 127.0.0.1 and the fake compute pool from `@open3dj/mcp`. Key-like test strings are built at run time.

- `sse.test.ts`: every chunk size, CRLF and CR split between chunks, field rules, the byte order mark, the end of the stream and the cap.
- `stream.test.ts`: every block type, usage, stop details, tool input parsing, unknown block and delta types, the error event and broken streams.
- `client.test.ts`: headers, retries and their limit, `retry-after`, network errors, error words, redirects that are never followed, redaction, the base URL rules and `listModels` pagination.
- `api-engine.test.ts`: a turn with two tool rounds on the real handlers (requests that extend each other, one user message of results per reply), the request shape and caching, the injected `base_rev`, invalid tool input, `maxRounds`, the budget, every stop reason, Stop mid-stream and mid-tool, the time limit, thinking blocks, errors, retries, the preview cap, and the key never leaking.
- `approval.test.ts`: the payload and its hash, a wrong hash, expiry on an injected clock, the scope rules and finality.
- `ledger.test.ts`: the defaults, what counts, the floor at 0, refused caps and usage, and no way to raise a cap.
- `egress-log.test.ts`: the file and folder modes, append-only lines, schema checks, and no prompt text or key.
- `api-tools.test.ts`, `results.test.ts`, `prompt.test.ts` and `index.test.ts`: the first slice, the exports, the dependencies, and a child process that imports the package and checks that no kernel or compute worker module is resolved.

```sh
npm test -- packages/agent
```
