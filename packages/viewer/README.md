# @open3dj/viewer

The browser viewer of step S2 ([PLAN.md](../../docs/PLAN.md) S2, [ARCHITECTURE.md](../../docs/ARCHITECTURE.md) sections 12 and 13). `open3dj view` serves it (see [packages/open3dj](../open3dj/README.md)):

```sh
npx open3dj view examples/enclosure/enclosure.o3j.js
```

The page is plain ES modules with no bundler and no build step. It loads three.js 0.186.1 (MIT, the one runtime dependency) through an import map: the core builds, OrbitControls, RoomEnvironment and the fat-line add-ons (LineSegments2, LineSegmentsGeometry, LineMaterial, and the WebGPU LineSegments2).

## Files

| File | Holds |
|---|---|
| `src/index.ts` | The Node side: `viewerAssets()` (the fixed table of files a server may serve), `viewerPage(title)` (the HTML with its import map and Content-Security-Policy), `IMPORT_MAP`, `THREE_VERSION` |
| `web/index.html` | The page: toolbar, tree panel, 3D view, selection, view tools, measure and fits panels, status bar, help overlay |
| `web/main.js` | Start-up, renderer choice, on-demand rendering, data loading, the event stream, tree, selection of parts and elements, sharing the selection with agents, the agent's highlight, keyboard, theme, screenshot and the frame-time probe |
| `web/camera.js` | Orthographic and perspective cameras, OrbitControls, mouse presets, standard views, fit-to-view |
| `web/scene.js` | `ModelScene`: `InstancedMesh` per definition and colour (or one `BatchedMesh`), merged edges, caps, overlays, fit markers, picking, highlights (hover, selection, measure picks and the agent's targets) |
| `web/tools.js` | The view tools: section plane, exploded view, x-ray, measure, analysis overlays, quality settings |
| `web/faces.js` | B-rep faces and edges from the tessellation, and element names (pure functions, tested in Node) |
| `web/measure.js` | Measure math on the mesh (pure functions, tested in Node) |
| `web/analysis.js` | Explode offsets and the overhang and draft classes (pure functions, tested in Node) |
| `web/glb.js` | Reads the GLB the export job writes into parts with occurrence paths and world matrices |
| `web/fits.js` | Fit marker positions, labels and pair counts (pure functions, tested in Node) |
| `web/viewer.css` | Layout and the dark and light themes |

## What the page does

- **Renderer.** three.js `WebGPURenderer` when `navigator.gpu` gives an adapter, else `WebGLRenderer` on WebGL2. If the WebGPU device fails after start-up (a lost device, or a software adapter that cannot map buffers), the page reloads itself once on WebGL2. With neither context it says so and shows the CPU hidden-line drawing of the same revision. `?renderer=webgl` or `?renderer=none` forces a path, for tests. The status bar says "(software)" when the adapter is a software rasteriser (SwiftShader, llvmpipe).
- **On-demand rendering.** A frame is drawn only when the camera, the scene, the selection, a tool or an overlay changes, and while a view animation or damping runs. Idle draws were already zero before this rework (the old loop skipped the draw when nothing changed); the page now also stops requesting animation frames when idle, so an idle tab runs no callback at all.
- **Model.** Units are mm and Z is up, as in the GeometryReport. The GLB's root node converts to metres and Y-up; the viewer drops that one transform. Every occurrence of a definition shares one `BufferGeometry`, drawn as one `InstancedMesh` per definition and colour. When an assembly has more than 24 such groups, every part goes into one `BatchedMesh` instead: one multi-draw call, with each instance culled against the view on its own. The Quality panel (or `?batch=on|off|auto`) chooses. An `InstancedMesh` is culled as a whole by the bounding sphere of its instances, which is recomputed whenever a part is hidden, isolated or exploded.
- **Faces and element addresses.** The export job writes the kernel's tessellation into the GLB unchanged: OCCT meshes each face on its own, in the kernel's face order, and never shares a vertex between two faces. `faces.js` splits each definition's triangles into those runs. A run is the face `face:<n>` (the element address used in errors and `inspect`) only when the runs are in one piece each and as many as the kernel's face count for that definition in the report; otherwise the panel says why there are no addresses. `src/elements.test.ts` holds that order against the kernel itself.
- **Edges.** The edges drawn are the B-rep edges: the seams between faces (the seam of a periodic face, such as the side of a cylinder, is left out, as CAD views do). They are merged for the whole assembly into one line object, one draw call, with per-vertex colours for the selection. Fat lines (`LineSegments2`, 1.6 px) are a Quality option.
- **Picking.** A ray cast on the CPU finds the occurrence and the triangle; the triangle gives the face by a binary search in the face's triangle ranges. An edge of that face wins over the face when the cursor is close to it: within 4 pixels on a face that is large on screen, and within 10% of the face's size on screen on a small one, so a click on a zoomed-out assembly keeps the face and its address (zoom in to pick edges). With a section on, a click on a cap selects the part that was cut, with no face address, never a face hidden behind the cap. Hover shows a faint fill and the face's outline (the outline only while an analysis overlay shows its colours). A click selects the part and the element, `Shift`+click or `Ctrl`+click adds. A part with a picked face or edge is tinted only lightly; the face is filled in a second, stronger tone and outlined in the accent at 3 px, so it stands out from the rest of its part. The selection panel names the element (`lid@elem:face:5`); `C` copies the addresses. The kernel numbers edges in an order the mesh does not carry, so an edge is named by the two faces it joins (`lid: the edge between face:1 and face:5`), never as `edge:<n>`.
- **Shared selection.** With "Share with agents" on (the default, kept in local storage), the selection goes to the server 250 ms after it last changed: occurrence paths, and for picked faces the kernel's face number with the observed area, centroid and normal (in the definition's frame), for picked edges the faces they bound and the observed length. The server checks it against the revision and keeps it in the project (`.o3j-view/selection.json`), where an agent reads it with `inspect fields=[selection]`. The panel says what agents see. Clear empties the selection here and for agents; turning sharing off clears it too.
- **Agent highlights.** When an agent calls `render view=highlight` with targets (occurrence paths, definitions or `<path>@elem:face:<n>`) and an optional note, the server checks the file and sends it on the event stream. The page fills face targets in the agent colour (magenta) and leaves their parts untinted, tints parts named whole, draws every target's edges through the parts in front of it (so a screw inside the lid still shows), rings the targets' swatches in the tree, and shows "Pointed at in this project" with the targets and the note (as text). It never moves the camera: Frame (or `A`) frames the targets with at least a quarter of the assembly around them and shows them again if they were hidden, and a target in the banner is a button that selects and frames that target. Faces are filled only on the revision the highlight names. Dismiss (or `Shift`+`A`) hides the highlight for this browser tab until it changes. The banner says where the highlight comes from (`render view=highlight`, usually your agent), because any local process can write the file.
- **Tree.** Every occurrence with its path, definition and validity. A click selects, `Ctrl`+click or `Shift`+click adds, a double-click fits that part. The eye button hides or shows it.
- **Selection panel.** The report numbers of the selected occurrence's definition (volume, area, mass, size, local bounding box, centre of mass, counts), the world box of that occurrence, and the picked faces and edges with their observed area, normal or length.
- **Section.** A plane on X, Y or Z with a slider over the assembly box; when switched on it keeps the side away from the camera, the panel says which side it keeps ("keeps below"), and Flip side keeps the other. The position shows as many decimals as the slider step resolves. Cut solids show a filled cap: the back faces seen through the cut are drawn flat in a darker shade of the part's colour (a true stencil cap with hatching is not done). Picking ignores the cut-away side and picks caps as their part. With x-ray on, the caps are hidden so the inside shows.
- **Exploded view.** A slider moves each occurrence away from the assembly centre along the line to its own centre (0 to 150% of that distance). View only: nothing is written, and measures use the assembled positions. When the slider is let go and parts left the view, the view frames them again. Fit markers are hidden while the view is exploded, because the parts no longer touch.
- **Measure.** `R` or the Measure button. A click picks a face, an edge or a point; a second click measures between the two: point to point distance with its components, the angle between two planar faces, and the distance between parallel planes. The same face picked twice is two points on it (no angle or plane gap). A face shows its area and normal, an edge its length. These are observed on the display mesh, within the export chord of the true surface. For two different occurrences the panel adds the kernel's minimum distance or overlap from the report's fit lines, labelled measured; when the report has no line for the pair, a plain note says so. Each result row puts its label (often a long element address) on its own line with the value below it, and the panel scrolls into view.
- **X-ray.** `X` makes the parts see-through with their edges drawn, so inner parts and fits show.
- **Analysis overlays (preview).** `O` cycles Off, Overhang and Draft. Overhang uses the build direction +Z: a surface that leans more than the limit (default 45 degrees) past vertical is red, and faces that rest on the bed (the part's lowest level) are blue. Draft takes a pull direction and a minimum draft (default 1 degree): positive, negative and insufficient draft get their own colours. The legend gives the area of each class. These are previews computed on the mesh in the browser; the CPU kernel decides gates of record (S3 for the FDM overhang gate, S9 for draft), as [COMPUTE.md](../../docs/COMPUTE.md) "GPU screens, CPU decides" requires.
- **Numbers and their labels.** "measured" marks numbers from the CPU kernel (the report); "observed" marks numbers read off the display mesh; "preview" marks the overlays.
- **Lighting.** Image-based lighting from three's `RoomEnvironment` through a PMREM, with a hemisphere light and a headlight that follows the camera. It starts on with a hardware GPU and off with a software rasteriser, where it costs more than it gives; the Quality panel (or `?env=0|1`) changes it.
- **Quality and performance.** The pixel ratio is capped at 2 by default (Quality panel, or `?dpr=`). While the view moves and frames take longer than 40 ms, the page draws at half the pixel ratio and draws one full frame 250 ms after the motion stops (Quality panel, or `?adaptive=0`). Frame times measured with it on are not frame times at the stated resolution: `npm run viewer:bench` turns it off.
- **Screenshot.** `Shift`+`S` or the PNG button downloads the current view as a PNG.
- **Frame-time probe.** The Quality panel's readout (or `?perf`) shows frame time p50 and p95 while the view moves, draw calls, triangles and the pixel ratio of the last frame (updated after the full-resolution frame that follows a motion, with "half while moving" when adaptive resolution was used). `window.open3dj.perf()` returns the same numbers plus pick times and scene counts, and `window.open3dj.probe(ms)` orbits the camera for ms milliseconds without the mouse and returns them; that is the probe for the S2 frame-time gate.
- **Fits.** Clash, contact and clearance lines from the report, clashes first. The header counts each pair once, by its closest relation; further gaps of a pair (report lines marked `extra`) are counted apart and labelled "further gap". When an extra line is its pair's only line (a mated lid: the seat contact is not listed, the lip clearance is), it counts as that pair's relation and says "beside a mated seat". `open3dj run` and `open3dj inspect --fields fits` use the same words. A marker sits between the two parts' world boxes: in the middle of their overlap, or in the middle of the gap between them. A click selects both parts and frames them. A marker is hidden while either part of its pair is hidden or left out of an isolated set. Markers are drawn as one `InstancedMesh` per kind, 5 pixels in radius at any zoom (measure marks 4 pixels), so they never cover a part you zoomed in on.
- **Status bar.** Revision, report status and valid definitions, the compute block, the renderer, the last run (or its error and line), the frame-time readout when on, and the live link state.
- **Navigation.** Presets: Open3DJ (left orbit, right pan), SolidWorks (middle orbit, `Ctrl`+middle pan) and Onshape (right orbit, middle pan). The wheel zooms at the cursor. Orthographic by default; `P` switches to perspective. The preset, projection, theme, edges, markers and quality settings are kept in the browser's local storage when it allows that.
- **Theme.** Dark or light, following the system until you press `T`.

Press `?` in the page for every shortcut. Shortcuts follow the Shift key, not the letter case (Caps Lock changes nothing), and they keep working while a slider or a checkbox has focus; only controls that take typed text hold them back.

## Measured

`npm run viewer:bench` (`scripts/viewer-bench.ts`) measures load to first frame, frame time p50 and p95 during `open3dj.probe` and during a mouse orbit, draw calls, triangles and the JS heap for `examples/enclosure`, `plate-145` and `grid-1025`, with WebGL2 and, when the browser has a working adapter, WebGPU. It needs Playwright and skips without it. Its results, with the machine, are in [ops/build-log.md](../../ops/build-log.md). The table below is the before-and-after of the performance rework.

Measured on 2026-10-31 in headless Chromium with WebGL2 on SwiftShader (a software rasteriser: there is no GPU on this machine), 4 vCPUs shared with other jobs, a 1280 x 800 view. **Every frame of both sides is drawn at pixel ratio 1**: the page is opened with `?adaptive=0`, so neither side halves the resolution while the view moves. (An earlier version of this table compared full-resolution "before" rows with "after" rows drawn at half resolution while moving; it overstated the orbit gains.) Frame times here are dominated by the software rasteriser and vary by tens of milliseconds between runs; they are not the S2 gate, which is measured on a GPU. Draw calls and triangles are counted per frame on the WebGL2 context.

Each row is two runs of the viewer before this change (`git` HEAD of 2026-10-31) and two after, interleaved, with the GLB already cached on the server. "Load" is page start to the first drawn frame; "orbit" is the interval between frames while a left drag orbits the view for 3 s; "probe" is `open3dj.probe(3000)`, which orbits without the mouse; "pick" is one hover pick (ray cast plus the nearest-edge test) over 40 pointer positions. The "after" draw calls include the hover outline of the face under the cursor.

At equal resolution on SwiftShader the orbit frame time of `examples/enclosure` did not improve, and the gains on the reference assemblies are small (`plate-145` p95 233 to 283 ms before and 233 ms after; `grid-1025` p95 200 to 233 ms before and 200 ms after): a software rasteriser spends its time filling pixels, not issuing draw calls. The draw-call cut (433 to 7, 1,030 to 7) is what a GPU driver feels, and the S2 gate needs a GPU run to show it. Idle draws were already zero before; the page now also stops requesting animation frames when idle (120 empty callbacks in 2 s before, 0 after). With adaptive resolution on (the page's default), frames drawn while moving are at half the pixel ratio and faster; `npm run viewer:bench -- --with-adaptive` reports those as separate rows that never count for the gate.

Where the numbers come from: one draw call per definition and colour, one for all edges, and one per fit kind, instead of one edge object and one marker mesh per occurrence; fewer triangles because the fit markers are lower-poly spheres, now 5 pixels in radius on screen (the 286 markers of `plate-145` were most of its triangles). Load takes longer because each definition's faces and edges are found once on load (about 190 ms for the 144-hole plate). Picking stays under 8 ms on the CPU (p95 on `plate-145`), so three-mesh-bvh is not added.

## The server contract

`open3dj view` (`packages/open3dj/src/view.ts`) serves these routes, all under `/<nonce>/` and all GET or HEAD:

| Route | Answer |
|---|---|
| `/<nonce>/` | The page, with a CSP that allows only its own files and the hash of the inline import map |
| `app/<file>`, `vendor/<file>` | The files in `viewerAssets()`: the modules in `web/` and nine three.js files (`vendor/addons/...` keeps the add-ons' folder layout, so their relative imports resolve) |
| `api/model` | `{project, rev, head, run, tree, definitions, report, parts, fits, glb, drawing}` for the head revision; `parts` are the detailed measures, whose face counts decide element addresses |
| `api/rev/<rev>/model.glb` | The revision's GLB from the export job on the compute pool, cached per revision |
| `api/rev/<rev>/drawing.png` | The revision's four-view hidden-line drawing from the render job |
| `api/events` | Server-sent events: `hello` (with the last agent highlight while it is under 15 minutes old), `run` (running, done or error with the ScriptError), `revision`, `selection` (the stored selection after a write) and `highlight` (a new, checked agent highlight) |
| `api/selection` (GET) | The shared selection (`viewer-selection` schema), rebuilt from its revision on every read, or `{items: []}` |
| `api/selection` (POST) | The one write: the page's selection, `{rev, items: [{path, face?, edge_faces?, observed?}]}` (`viewer-selection-input` schema); `items: []` clears it. Answers the stored selection |

Security (ARCHITECTURE.md section 12): the server binds 127.0.0.1 only; the nonce is 24 random bytes per session; the Host header must name the loopback port; a request with an Origin from another page, or with `Sec-Fetch-Site` cross-site or same-site, is refused; there are no CORS headers. GET and HEAD are answered on every route, and POST on `api/selection` only, with stricter checks: the Origin must be present and be the page's own, `Sec-Fetch-Site` must be same-origin when sent, the type must be `application/json`, the `Content-Length` 16 KiB or less (no chunked bodies), and a token bucket allows 20 writes, refilled at 5 a second (429 beyond). The body must match the schema, name parts of a stored revision and face numbers within the kernel's face count; the server adds the definition, address and reference fingerprint itself and writes `.o3j-view/selection.json` and nothing else. The agent's `.o3j-view/highlight.json` (written by `render view=highlight` in any process) is polled every second and checked before the page sees it: the schema, a time that is not in the future (so the 15-minute replay cannot be stretched), and every target resolved again on the revision to exactly its paths and face (so a target is a name from the design, never free text). Both files are untrusted on read, because any local process, or a cloned project, can put them there: the selection is rebuilt from the revision each time it is read, and it says what was clicked, never what was approved. A request path is looked up in a fixed table and never joined onto a folder, so it cannot reach files outside the project outputs and the viewer assets.

## Not yet

- `edge:<n>` addresses. The kernel numbers edges by walking each face's wires, and the mesh does not carry that order. An edge is named by its two faces until the export writes the kernel's edge ranges next to the mesh (occt-wasm's `meshShape` face groups and `wireframe` edge groups give both).
- Exact face and edge numbers from the kernel in the measure tool (face area, edge length, the distance between two picked elements). They need a read-only kernel job for elements, such as `inspect` with element targets; until then the tool shows observed mesh numbers, and the kernel's part numbers and fit distances.
- Level of detail. The server cannot tessellate at a second, coarser deflection: the GLB comes from the export job at the export chord, and the viewer has no kernel. A coarse LOD for far or tiny parts needs the export job to write a second mesh per definition.
- GPU picking. Picking is a CPU ray cast on the instanced meshes, which takes a few milliseconds on the reference assemblies (`open3dj.perf().pickMs`); a BVH (three-mesh-bvh) or GPU ID buffer is worth adding when a real assembly makes picking slow.
- The S2 frame-time gate needs a GPU: the only test machine renders with SwiftShader. The WebGPU path is written and starts, but it was not seen rendering on real GPU hardware.
- Fit markers come from bounding boxes, because the report does not carry a contact location yet. Parts whose boxes nest (a pin inside a hinge) put their markers at one point, and the further gaps of a pair share the pair's point.
- Approvals and the exploded-step editor arrive in later steps (S4, S5). The exploded view here is view only.
