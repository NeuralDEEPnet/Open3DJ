# Security Policy

Open3DJ is open-source, agent-first CAD created by Neural Deep Network LTD. Security matters more here than in most desktop tools. Open3DJ is designed to run code that its users did not write (scripts generated by AI agents). It opens files that come from the internet (STEP, 3MF, STL, SCAD and others), and it exposes a local MCP server that other programs can reach. Our research found real incidents on every one of those surfaces in 2025 and 2026 ([docs/research/security-sandboxing.md](docs/research/security-sandboxing.md)).

Thank you for helping keep Open3DJ and its users safe. Good-faith reports are always welcome, and we credit reporters publicly unless you ask us not to.

## Supported versions

Open3DJ is in the planning stage. **No version has been released yet**, so no version is currently supported.

| Version | Supported |
|---|---|
| No releases yet | Not applicable |

Once the first preview ships, security fixes will go into the latest pre-release. Before 1.0, only the most recent release line receives fixes. We will update this table with each release.

You are still welcome to report problems in the design documents, such as a weakness in the planned sandbox or MCP design described in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Catching these before code exists is the cheapest fix of all.

## How to report a vulnerability

**Please do not report security vulnerabilities in public issues, discussions or pull requests.**

Report privately through GitHub private vulnerability reporting:

1. Go to the [Security tab](https://github.com/NeuralDEEPnet/Open3DJ/security) of this repository.
2. Click **Report a vulnerability**, or open https://github.com/NeuralDEEPnet/Open3DJ/security/advisories/new directly.
3. Fill in the form. Only you and the maintainers can see the report.

> **Note for the founder:** private vulnerability reporting must be switched on before the button appears. In the repository go to **Settings**, then the **Security and quality** section (older interfaces call it **Code security**), then **Advanced Security**, and click **Enable** next to **Private vulnerability reporting**. The steps are also in [docs/REPO-SETTINGS.md](docs/REPO-SETTINGS.md).

If the **Report a vulnerability** button is not visible yet, message a maintainer privately via the contact page at https://www.neuraldeep.net. Ask for a private channel and do not include vulnerability details in that first message.

### What to include

A good report helps us act quickly. Please include as much of this as you can:

- The affected component and version or commit (for example the MCP server, the script sandbox, a file importer or a plugin).
- Your operating system and, if relevant, the MCP client or agent you used.
- Step-by-step reproduction, and a minimal proof-of-concept file or script.
- What an attacker can achieve, and what they need first (local access, a crafted file, a malicious web page, a malicious plugin and so on).
- Any fix or mitigation you suggest.

If an AI tool helped you find the issue, that is fine. Please say which tool, and confirm the issue with a working reproducer before you send it. Unverified automated reports take a lot of volunteer time to check, and we may close them without detailed review.

## What is in scope

Everything in this repository is in scope: the code (once it lands), the build and release pipeline, and the documented security design. These areas matter most to us:

| Area | Examples |
|---|---|
| **Sandbox escapes for agent-run scripts** | A script reaches the network, the file system, the clock, host objects or other processes when it should not. A script breaks out of the interpreter, WASM or operating-system sandbox. A script bypasses CPU, memory, time or output limits in a way that harms the host. |
| **MCP server issues** | Prompt injection through file contents, such as STEP header fields, 3MF metadata, SCAD comments, part library text or file names, that makes an agent take an action the user did not approve. Untrusted file text that reaches tool descriptions or system prompts. Tool descriptions or schemas that change after the user approved them. Bypass of human approval steps. |
| **DNS rebinding and localhost exposure** | Missing or weak `Origin` or `Host` validation. CSRF from a web page against the local server. The server listening on `0.0.0.0` or a public interface. Access without the per-install token. |
| **Token and secret handling** | Tokens or API keys stored in plain text, written to logs, or placed in URLs. Session IDs used as credentials. Token passthrough to other services. Unsafe handling of OAuth redirects or URL schemes. |
| **Plugin and model supply chain** | Unsigned or tampered plugins or packages. Model weights in formats that can run code (such as pickle files). License or territory manifests that misstate what a model pack is. Dependency confusion or typosquatting on Open3DJ package names. Compromise of the build or release pipeline. |
| **Path traversal and file handling** | Reads or writes outside the project or export folder. Symlink or path-prefix tricks. Archive extraction that writes outside its target ("zip slip"). Memory-safety bugs in STEP, 3MF, STL, SCAD or other importers. |
| **Data leaving the machine** | Geometry, metadata or credentials sent to a cloud provider (3dj.app included) without the user's explicit consent for that job. |
| **Geometry integrity** | Silent changes to geometry, dimensions, tolerances or evidence reports. A wrong tolerance on a manufactured part can be a safety issue. |

For prompt injection, the test is a permission boundary. A report is in scope when injected content causes an action, a data flow or a file change the user did not approve, or hides information from the user. An agent that merely says something wrong is a quality bug, not a vulnerability. Please file those through the normal [bug report form](https://github.com/NeuralDEEPnet/Open3DJ/issues/new/choose).

## What is out of scope

- Hosted services, including 3dj.app. It is a separate, closed product run by Neural Deep Network LTD. Contact the company via https://www.neuraldeep.net about it. This policy does not authorize testing it.
- Bugs in upstream projects such as Open CASCADE Technology, Manifold or MCP client software. Please report them upstream. If the bug affects Open3DJ users, tell us too and we will help coordinate.
- Reports from automated scanners with no demonstrated impact.
- Denial of service on your own machine through a deliberately huge model that stays within the documented limits.
- Social engineering of maintainers or contributors, and physical attacks.

## What you can expect from us

Open3DJ is run by a small volunteer team with the help of AI agents. There is no paid security team, so these are honest targets rather than guarantees:

| Step | Target |
|---|---|
| Acknowledge your report | within 7 days |
| First assessment (confirmed, needs more information, or not a vulnerability) | within 14 days |
| Status updates while we work on it | at least every 14 days |
| Fix for a confirmed critical or high-severity issue | aim for 30 days after confirmation |
| Fix for other confirmed issues | in a following release |
| Public disclosure | coordinated with you. By default when a fix is released, or after 90 days, whichever comes first, unless we agree otherwise |

If we are going to miss a target, we will tell you. We publish fixes as GitHub security advisories and request CVE IDs through GitHub where appropriate. We credit reporters in the advisory and in the release notes.

We cannot offer a paid bug bounty yet. Our research recommends a sandbox-escape bounty in the future ([docs/research/security-sandboxing.md](docs/research/security-sandboxing.md)), and we will announce one if funding allows.

## Safe harbor

We support good-faith security research on Open3DJ. If you follow this policy, we consider your research authorized:

- We will not pursue or support legal action against you for research that follows this policy.
- We will not report you to law enforcement for it.
- If a third party takes legal action against you for research that followed this policy, we will make it known that you acted in line with this policy.

Good faith means that you:

- Test only Open3DJ software that you run yourself, on systems and accounts you own or have permission to use.
- Do not access, change or delete other people's data, and stop as soon as you reach data that is not yours.
- Avoid harm: no denial-of-service attacks against shared infrastructure, no spam and no social engineering.
- Report the issue to us privately and give us reasonable time to fix it before you disclose it.

This safe harbor covers Open3DJ software that you run yourself. It does not authorize testing against hosted services, including 3dj.app, or against other people's machines. If you are unsure whether something is in scope, ask us first through a private report.

## Security design, in brief

Open3DJ is still being designed. The planned approach, from [docs/research/security-sandboxing.md](docs/research/security-sandboxing.md), is:

- Layered sandboxing for scripts: a small, deterministic geometry API with no network, clock, randomness or file access, run in an interpreter compiled to WebAssembly with memory and time limits, inside an operating-system sandbox.
- An MCP server that uses stdio by default. Its HTTP mode listens on localhost only, validates `Origin` and `Host`, and requires a per-install token stored in the operating system keychain.
- All text that comes from files is returned to agents as labeled untrusted data and is never mixed into tool descriptions.
- Signed plugins, and model weights accepted only in safe tensor formats.
- Explicit per-job consent, and metadata stripping, before any geometry leaves the machine for a cloud GPU.

The design will be documented in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Every confirmed vulnerability becomes a regression test, in line with our "stop the line" practice described in [GOVERNANCE.md](GOVERNANCE.md).

## Advice for people who run agents on Open3DJ

- Run coding agents with the least access they need. Do not give an agent access to secrets it does not need.
- Treat files, issues and comments from other people as untrusted input for your agent.
- Never paste tokens, API keys or private designs into public issues, discussions or pull requests.
