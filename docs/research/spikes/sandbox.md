# Spike: Sandbox for agent-written scripts (2026-10-28)

One agent ran this spike, and a second, independent agent then reran and challenged it. Both sections are below. The machine was a shared 4-vCPU Linux x64 container with other agents running, so treat timings as noisy medians. The agents were not allowed to write report files, so this report was assembled from their structured results. Source code is in [sandbox/src/](sandbox/src/). Paths starting with `spikes/` or `scratchpad/` refer to the working folders where the spikes ran; outputs and installed packages are not in the repository.

**Question:** Can Open3DJ run untrusted agent-written 3dj-style JavaScript safely and fast enough in QuickJS (quickjs-emscripten), with the occt-wasm kernel reachable only through host functions that pass opaque integer handles? What are the costs, does each limit really hold, and what should the Step 1 sandbox design and the later OS-level layer be?

## Original run

**Verdict:** works-with-caveats

### Results

- VERSIONS: Node v22.22.0 on a 4-vCPU Linux x64 container (shared, noisy). quickjs-emscripten-core 0.32.0 (2026-02-16, MIT) with @jitl/quickjs-wasmfile-release-sync 0.32.0 (QuickJS 2025-09-13+f1139494), quickjs-ng variant 0.32.0 (quickjs-ng v0.12.1) and the asyncify variant 0.32.0. @sebastianwessel/quickjs 3.1.0 (MIT; deps memfs Apache-2.0, rate-limiter-flexible ISC). ses 2.3.0 (Apache-2.0). occt-wasm 5.8.1 (OCCT 8.0.1). All installed with --ignore-scripts. isolated-vm 7.0.1 was not tested: it is a native addon, and the safety rules forbid running package binaries.
- BRIDGE: the guest DSL facade runs inside QuickJS and holds only integer handles. A per-run host table maps 1, 2, 3, ... to kernel handles. Each host op has a typed signature (n = finite number, h = integer handle, s = string). Edge queries for fillet run on the host in a single call. subtract/union collapse into cutAll/fuseAll. The realistic part comes out bit-identical through the bridge and direct: 154,286.799 mm3, the same as the earlier occt-wasm spike.
- CALL COST (median of 5 fresh processes): a host no-op takes 3.40 us per call with Bellard QuickJS (34.5 ms for 10,000 calls), 3.15 us with quickjs-ng and 3.44 us with asyncify. With 3 numbers or one 64-char string it is 4.29 / 4.66 us. Through the validated bridge: no-op 3.37 us, add3 4.43 us. A guest-to-guest call is 0.045 us, and a direct Node call is 0.01 us. A host call is about 75x a guest call, but still negligible next to kernel ops that take milliseconds.
- VM CREATION: cold module load 20.3 ms (QuickJS) / 15.5 ms (ng). Runtime+context create and dispose: 0.27 ms. Full per-run setup (prelude plus in-guest intrinsic freeze): 4.2 ms, of which the freeze is about 3 ms (1.1 ms without it). A fresh wasm instance from a precompiled WebAssembly.Module with a capped memory: 1.6 ms.
- REALISTIC SCRIPT (median of 3 processes x 21 runs): the enclosure (box, fillet of 12 edges, 4 holes via cutAll, boss; 14 kernel ops) takes 48.4 ms direct and 54.5 ms through the bridge, +7.3 ms (15%). That splits into 4.5 ms setup, 0.9 ms guest plus marshalling and 0.45 ms teardown. The plate with 100 holes (202 kernel ops) takes 203.6 ms direct and 215.6 ms bridged, +13.3 ms (6.6%), with guest plus marshalling at 2.1 ms. quickjs-ng: enclosure +7.8 ms, plate +3.4 ms. The same prelude in an SES Compartment: 53.5 ms.
- WORKER DESIGN: spawn to ready takes 184 ms (in-worker kernel and QuickJS init 140 ms). A warm round trip for the enclosure, including STEP export, takes 74.8 ms. Of that, the fresh QuickJS instance is 1.6 ms and postMessage overhead is 1.1 ms. worker.terminate() stops a running OCCT call in 13-23 ms.
- CPU LIMIT: the interrupt deadline stopped while(true), a loop that catches the interrupt, ReDoS /(a+)+$/ and a looping sort comparator, each at 2.01-2.04 s against a 2 s deadline, with 'InternalError: interrupted'. The interrupt cannot be caught and fires inside the regex engine. The handler's cost is in the noise (307 ms with it versus 327 ms without on a 3-million-iteration loop). Recursion with catch-and-retry overshot to 4.66 s. The interrupt CANNOT fire inside a host or kernel call: fuseAll of 1,500 boxes ran 13.1 s despite the 2 s deadline in the naive design, and only the main-thread watchdog stopped it (worker killed at 5.0 s, then respawned).
- MEMORY LIMIT: rt.setMemoryLimit() bounds only SINGLE allocations in quickjs-emscripten 0.32.0, for both QuickJS and ng (upstream issue #271, open since Aug 2026; #255 is related). Under a 64 MiB limit, QuickJS reported 'memory used ... 1,401,172,938' bytes. The naive push loop grew the wasm heap to 611 MB and with no limit reached the 2 GiB wasm maximum after 12.7 s. FIX: build a fresh instance per run with newVariant(base, {wasmModule, wasmMemory: new WebAssembly.Memory({initial:256, maximum:2048})}). That gives a hard 128 MiB cap: every memory bomb (array push, 1 MiB Uint8Array push, objects, 100 kB strings) ends in 'InternalError: out of memory' within 0.08-0.59 s, and the module stays usable.
- STACK LIMIT: on the main thread, any setMaxStackSize of 192 KiB or more let V8's native stack overflow first. 'RangeError: Maximum call stack size exceeded' escaped evalCode as a host exception, and the corrupt runtime then aborted on dispose with 'Aborted(Assertion failed: list_empty(&rt->gc_obj_list) ... JS_FreeRuntime)'. 128 KiB was safe on the main thread. In a Worker with resourceLimits.stackSizeMb=8, every limit up to 1 MiB gave a clean 'InternalError: stack overflow' or 'SyntaxError: stack overflow' (deep JSON.parse). setMaxStackSize(0) always fails, so never disable the limit.
- NO ACCESS: require gives ReferenceError 'require' is not defined. process.exit gives ReferenceError 'process' is not defined. fetch gives ReferenceError 'fetch' is not defined. A static import gives SyntaxError expecting '('. Dynamic import('fs') and import('std') are rejected with 'ReferenceError: could not load module 'fs''. typeof is 'undefined' for process, require, module, fetch, XMLHttpRequest, WebSocket, setTimeout, console, WebAssembly, Atomics, std, os, __k and Date. The Function-constructor, host-function-constructor and host-error-constructor escapes and eval all stay in the guest realm (typeof process === 'undefined'). Date is removed; a seeded Math.random gives identical values across runs, while native QuickJS Math.random differed between runs.
- INTEGRITY: in-guest freezing of intrinsics blocks prototype poisoning ('TypeError 'map' is read-only'; Object.prototype pollution gives 'object is not extensible'). WITHOUT the freeze, Array.prototype.map = () => [] silently turned subtract into a no-op: volume 1000 instead of the expected 874.3, a wrong-geometry attack with no error. Forged handles are rejected: new Shape(...) gives 'Shape cannot be constructed directly', and {id:1} gives 'expected a Shape'. box('10',1,1), NaN, -1 and 1e300 are all rejected with clear messages. The op budget (5,000), batch cap (1,000), result cap (64 kB; a 396 kB result was refused) and 2,000-char error truncation all hold.
- CRASH CONTAINMENT: in the final design (Worker + fresh capped QuickJS per run + watchdog), all 53 hostile cases and 2 simulated host crashes (a host op that throws; a worker that calls process.exit(70)) were contained. Every sanity build that followed succeeded, there were 3 respawns, and the parent stdout carried exactly 1 line. A host hang caused by dumping a thrown object with a looping getter (deadline disarmed) was killed by the watchdog at 5.0 s.
- STDOUT: OCCT's STEP writer prints a banner through console.log. A Worker created with {stdout:true, stderr:true} captured it (27 chunks, 1,026 bytes) and the parent's stdout stayed at exactly 1 line. Without capture, the parent stdout had 28 lines and would corrupt an MCP stdio stream.
- NODE vm WITH A FROZEN CONTEXT is NOT a boundary. box.constructor.constructor('return process')() returned process, with getBuiltinModule('child_process').execSync available and /etc/hostname readable. The same escape works through a thrown host error and through a returned host object. It works even with ZERO endowments: this.constructor.constructor('return process')() returned an object, because the frozen context object belongs to the host realm. timeout stops synchronous loops (ERR_SCRIPT_EXECUTION_TIMEOUT at 1,003 ms), but a promise-job loop escapes it and hung the host until the external kill at 8 s, unless microtaskMode:'afterEvaluate' is set. A memory bomb kills the whole process ('FATAL ERROR: Reached heap limit', SIGABRT). The Node docs themselves say vm is not a security mechanism. 10,000 calls took 0.83 ms.
- SES 2.3.0: lockdown takes 59 ms and creating a Compartment 0.05 ms; 10,000 calls take 1.34 ms. It blocked every escape ('Function.prototype.constructor is not a valid constructor'), proto poisoning, Date.now and Math.random ('secure mode ... throws') and import() (SES_IMPORT_REJECTED). But it has NO CPU limit (an infinite loop hung until killed at 8 s) and NO memory limit (the process died with SIGABRT). Use it as an integrity layer, not as a resource boundary.
- @sebastianwessel/quickjs 3.1.0: by default it exposes a Node-compat surface (process, Buffer, a stubbed fetch, setTimeout, console, env, and module emulation where import {join} from 'path' works). Host calls through env cost 215 us each, about 60x raw newFunction. It inherits the setMemoryLimit bug (the push loop ran until the timeout). In 3 of 8 runs, a timeout landing during its host-call marshalling CRASHED THE HOST PROCESS (exit 1, uncaught 'RuntimeError: Aborted(Assertion failed: list_empty(&rt->gc_obj_list), at: ../../vendor/quickjs-ng/quickjs-amalgam.c,12520,JS_FreeRuntime)').
- OS LAYER (child process, median of 5): a plain child takes 457 ms from spawn to result, and fs write, /etc/passwd read, process spawn and TCP to 1.1.1.1:443 are all allowed. With node --permission --allow-fs-read=<deps>,<src> it takes 430 ms; fs and child_process give ERR_ACCESS_DENIED, but TCP is STILL ALLOWED because Node 22's permission model has no network control. Adding unshare -rn (an unprivileged user namespace) takes 409 ms, and TCP gives ENETUNREACH. Confinement adds no measurable startup cost.
- OCCT HEAP: the occt-wasm.wasm memory is defined inside the module (min 128 MiB, max 4 GiB), not imported, so unlike QuickJS it cannot be capped from JavaScript. It must be bounded by recycling the worker or by an OS limit (cgroup memory.max or a Job Object).
- REPORT FILE: the harness refused to write spikes/sandbox/REPORT.md ('Subagents should return findings as text'), so the report content is in this structured output. All raw data is in spikes/sandbox/out/.

### Failures and caveats

- setMemoryLimit does not bound a runtime's total memory in quickjs-emscripten 0.32.0 (both QuickJS and ng), only single allocations. Under a 64 MiB limit QuickJS reported 'memory used ... 1,401,172,938'. The wasm heap reached 611 MB in the naive run and the 2 GiB maximum with no limit. This is upstream issue #271 (open). Workaround verified: a fresh instance per run with a capped WebAssembly.Memory.
- Stack overflow escaped as a host exception on the main thread whenever setMaxStackSize was 192 KiB or more: 'RangeError: Maximum call stack size exceeded' thrown out of ctx.evalCode, then 'Aborted(Assertion failed: list_empty(&rt->gc_obj_list), at: ../../vendor/quickjs/quickjs.c,2036,JS_FreeRuntime)' on dispose. This happened in the naive v1 run for the stack-recursion, stack-recursion-catch-retry, stack-json-parse-deep and stack-recursion-default-stack cases. Fixed by running in a Worker with resourceLimits.stackSizeMb=8 and a 256 KiB QuickJS stack. stackBytes=0 still fails, even inside the worker.
- The interrupt handler cannot stop a long kernel call: fuseAll of 1,500 boxes ran 13.1 s against a 2 s deadline. Only the watchdog (worker.terminate) bounds it.
- Disposing a runtime that still has live objects or pending promise jobs aborts the wasm module: 'Aborted(Assertion failed: list_empty(&rt->gc_obj_list) ...)'. This was seen after a drained microtask flood and after stack overflows. The module stayed usable, but memory leaked, which is one reason to use a fresh instance per run.
- The asyncify variant 0.32.0 fails on every runtime dispose after newFunction: 'QuickJSRuntime(rt = 5333520) not found when trying to free HostRef(id = -2147483648)' (33 dispose errors per benchmark process). Do not use it.
- Freezing guest intrinsics broke host error messages. ctx.newError(msg) assigns .message, which silently fails once Error.prototype is frozen (the 'override mistake'), so every host error reached the guest with message ''. Fixed by building errors with defineProp.
- Dumping a guest error can run guest code (getters, toJSON). With the deadline disarmed before ctx.dump, a thrown object with a looping getter hung the host until the external kill at 30 s. Fixed by keeping the deadline armed until extraction is done; the watchdog also covers it.
- Kernel errors leak raw kernel ids into the guest: 'fillet failed: fillet: operation failed [faulty edges: 469,470,...]'. Not fixed in the spike; Step 1 should map these to guest handles or strip them.
- Recursion with catch-and-retry overshot the 2 s CPU deadline to 4.66 s before being interrupted. The watchdog grace period (3 s here) must cover this.
- @sebastianwessel/quickjs 3.1.0 crashed the host process in 3 of 8 runs when its executionTimeout fired during env host-call marshalling (10,000 env.noop() calls, 2,000 ms timeout): uncaught 'RuntimeError: Aborted(Assertion failed: list_empty(&rt->gc_obj_list), at: ../../vendor/quickjs-ng/quickjs-amalgam.c,12520,JS_FreeRuntime)', exit code 1.
- Node vm and SES have no memory limit: the memory bomb killed the process with 'FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory' (SIGABRT). SES has no CPU limit either, and Node vm's timeout does not cover promise jobs unless microtaskMode is 'afterEvaluate'.
- Node 22's --permission does not restrict the network (a TCP connect to 1.1.1.1:443 still succeeded); a network namespace (unshare -n or -rn) is needed.
- Could not search upstream issues through gh: GraphQL and search are blocked in this session. The upstream issues were confirmed by fetching the GitHub issues page.
- Not tested: Windows and macOS, wasmtime, isolated-vm, a soak or leak test over thousands of runs, fuzzing of the bridge, and an end-to-end run with a real MCP client.
- The harness blocked writing REPORT.md, so the report exists only as this structured output.

### Recommendations for Step 1

- ENGINE: use quickjs-emscripten-core 0.32.0 with @jitl/quickjs-wasmfile-release-sync 0.32.0 (MIT), pinned exactly, with @jitl/quickjs-ng-wasmfile-release-sync as a drop-in fallback (same results, call cost within 10%). Do not use the asyncify variant (dispose bug, 2x size) or @sebastianwessel/quickjs (Node-compat surface, 60x call cost, host-crashing timeout path). Write the bridge ourselves on newFunction; it is about 250 lines.
- FRESH CAPPED INSTANCE PER RUN: compile the QuickJS wasm once, then for each run call newQuickJSWASMModuleFromVariant(newVariant(base, {wasmModule, wasmMemory: new WebAssembly.Memory({initial:256, maximum: 128 MiB / 64 KiB})})). This costs 1.6 ms and is the only hard memory cap that works. Also call setMemoryLimit, which still catches single huge allocations. Throw the instance away after each run, so leaks from aborted disposes cannot accumulate.
- LIMITS PER RUN: setMaxStackSize 256 KiB (never 0); an interrupt deadline of about 2 s that stays armed until every guest value has been extracted; caps of 5,000 kernel ops, 20,000 handles, 1,000 shapes per batch, 4 kB per string argument, and 64 kB of JSON result; guest error text truncated to 2,000 chars. Promise jobs are not drained, since the DSL is synchronous.
- DETERMINISM AND INTEGRITY: create the context without the Date intrinsic; install a seeded Math.random; run the DSL prelude first so it captures and deletes the hidden __k capability object; then freeze all guest intrinsics and globalThis. Without the freeze, poisoning Array.prototype.map silently produced wrong geometry. Build host errors with defineProp (override mistake). Give every host op a typed signature, use a per-run handle table so ids are never kernel ids, and wrap each run in kernel.checkpoint()/releaseSince().
- PLACEMENT: one sandbox Worker per session. Options: resourceLimits {stackSizeMb: 8, maxOldGenerationSizeMb: 512}, stdout: true and stderr: true (this keeps the OCCT STEP banner off the MCP stdio stream), env: {}. The main thread (the MCP server) runs a watchdog at cpuMs + 3 s that calls worker.terminate() (measured 13-23 ms) and respawns (cold start 184 ms). Recycle the worker after N runs or when kernel heap growth passes a threshold, because the OCCT heap (up to 4 GiB) cannot be capped from JavaScript.
- BOUNDARY API: define the sandbox interface as run(code, params, limits) -> plain JSON {ok, parts[{name, color, volume, valid}], error{kind, name, message}, timings, stats}, with error kinds cpu-timeout, guest-error, result-too-large, bad-result, watchdog-killed, worker-exit and host-exception. That lets the same module move unchanged from a Worker to a child process. Treat every guest-originated string as untrusted data when it goes back to the agent. Map kernel ids in error messages (for example 'faulty edges') to guest handles.
- OS LAYER NEXT (Step 1.x): run the same worker module as a child process started with node --permission --allow-fs-read=<app dir only> and the environment reduced to PATH. Wrap it in a platform sandbox: Linux bubblewrap or unshare -rn plus Landlock and seccomp, plus a cgroup memory.max (which also caps the OCCT heap); macOS Seatbelt (sandbox-exec profile with no network); Windows AppContainer plus a Job Object with memory, CPU and kill-on-close. Measured confinement startup cost: none (409-457 ms spawn to first result in every configuration). This layer is required before the native OCCT backend, where a failed fillet can segfault the process (gap-8). Longer term, add wasmtime with fuel and epoch as a second WASM wall, per security-sandboxing.md.
- NEVER use Node vm (escape even with zero endowments) or SES alone (no CPU or memory limits) as the boundary. SES could later serve as an extra integrity layer on the host side.
- Add these spike suites to CI as regression tests: the 55 hostile cases through the worker (src/lib/cases.mjs, src/worker-suite.mjs), the one-line-stdout check, and the bit-identical volume check (bridge versus direct). Add a soak test (10,000 runs per worker) and fuzzing of op arguments before the Agent Preview. Track upstream quickjs-emscripten issues #271 and #255, and re-run exp-mem-min.mjs on every version bump.
- Teach the agent guide to batch: one cutAll or fuseAll instead of loops of single booleans. The per-call bridge cost is irrelevant (3-4 us), but long single kernel calls are only bounded by the watchdog.

- ## Independent reproduction (Node v22.22.0, 4 vCPU, shared with other agents; the author's raw data was kept in sandbox/out-original/ before the rerun; versions checked after npm install --ignore-scripts: quickjs-emscripten-core 0.32.0, @jitl/* 0.32.0, occt-wasm 5.8.1, ses 2.3.0, @sebastianwessel/quickjs 3.1.0)

The asyncify runs still log 33 dispose errors ('QuickJSRuntime ... not found when trying to free HostRef'), as the original did.
- REPRODUCED, cadbench (median of 3 processes x 21 iterations): quickjs enclosure direct 48.4 -> 49.9 ms, bridge 54.5 -> 54.7 ms, overhead 7.3 -> 4.8 ms (15.4% -> 9.6%). quickjs plate100 direct 203.6 -> 198.5 ms, bridge 215.6 -> 206.1 ms, overhead 13.3 -> 16.7 ms. ng enclosure overhead 7.8 -> 7.7 ms. identical_volume_all is true everywhere. - REPRODUCED, final Worker design (worker-suite.mjs): stdout is exactly 1 line, 55 cases, all_sanity_ok true, respawns 3 (two watchdog kills and one simulated exit(70)), as in the original. All 55 case outcomes and kinds match. Cold start 184 -> 223 ms, worker init 140 -> 178 ms, enclosure round trip median 74.8 -> 110.8 ms, fresh capped QuickJS instance 1.6 -> 3.9 ms, terminate() 13-21 ms. Captured kernel stdout is 7182 bytes in both runs. With --no-capture, stdout carries 28 lines (the leak reproduces).
- REPRODUCED, naive in-process suite (security.mjs), with the diffs the author predicted: with the 256 KiB stack, stack-recursion is now a guest InternalError, not a host RangeError. On the main thread, stack-json-parse-deep, default-stack and no-limit still escape as host RangeErrors, so the 8 MB Worker stack is required. kernel-long-single-op takes 12.7 s unbounded in-process. getter-on-thrown-error-disarmed hangs until the 30 s external kill.
- REPRODUCED: exp-stack (on the main thread, json overflows the host at >=192 KiB; in an 8 MB Worker every size up to 1024 KiB stays inside the guest). exp-mem-min and exp-mem (a 64 MiB setMemoryLimit let the wasm heap grow to 1956-2048 MiB). exp-memcap (a 128 MiB WebAssembly.Memory cap gives a clean OOM in 72-632 ms and the module stays usable; a fresh instance takes 1.06 ms). The asyncify dispose abort. The node:vm escapes (process reachable 3 ways). SES escapes blocked, but SES has no CPU or memory bound (8 s SIGTERM; heap SIGABRT). @sebastianwessel/quickjs exposes process, fetch and env by default, costs 229 us per env call (original 215), and its host process exits with 1 on timeout in 3 of 8 runs. os-layer: --permission blocks fs and child_process but not TCP, and unshare -n blocks TCP.
- CHALLENGE 1 (CPU deadline, different inputs): the 2 s interrupt deadline is NOT time-based. QuickJS calls the handler only every ~10k bytecode branch or call events, so a loop whose body is one slow native builtin overshoots by a large factor. 'const s=x.repeat(4e6); for(;;) s.indexOf(y)' (12.3 ms per call) was interrupted after 31.8 s with the watchdog grace raised to 120 s (4 handler polls in total); on quickjs-ng it took 83.9 s. 20 JSON roundtrips over 3e5 objects ran 9.5 s with 33 polls. Under the default limits both cases end as watchdog-killed (5.01 s) with a worker respawn, not as a clean cpu-timeout. The Worker watchdog, not the interrupt handler, is the real CPU bound.
- CHALLENGE 2 (flakiness of a claimed clean result): stack-recursion-catch-retry, reported as cpu-timeout at 4655 ms, took 5000.92 ms in my worker-suite rerun (0.9 ms under the 5 s watchdog). In 12 targeted repeats (0 and 4 CPU burner threads) it was watchdog-killed 8 times (4/6 each). Classify it as 'bounded by the watchdog', not 'clean timeout'.
- CHALLENGE 3 (stdout fix, different method): occt-wasm binds console.log at module load (var out=console.log.bind(console)). Monkey-patching console.log after init STILL leaks 448 bytes (6 lines) per STEP export, which is a trap. Passing print/printErr through the documented OcctKernel.init({createModule: (o) => factory({...o, print, printErr})}) gives 0 bytes on stdout and captures 11 lines in-process. The Worker capture works, but it is not the only fix; the Worker is still needed for the watchdog.
- CHALLENGE 4 (memory claims, different inputs): confirmed that setMemoryLimit bounds single allocations only. Under a 4 MiB limit, 2e5 small objects used 14.4 MB and 2e4 1 kB strings used 20.6 MB, while a single 8 MiB ArrayBuffer and a 3e5-entry Map were refused. The 128 MiB wasm cap held near the edge: after filling to OOM (1297 arrays), bounds() x200, kernel errors and 50-part returns all worked, and sanity runs passed. 40 back-to-back cap-filling runs kept RSS flat at 253-271 MiB, so discarded instances are reclaimed. NEW: OCCT memory is not bounded per run and never shrinks. Two in-budget runs with cpuMs raised to 120 s pushed RSS from 128 to 962 MiB, and it stayed there. Under the default limits a 100-sphere fuseAll left 259 MiB of high-water memory until the next respawn. The worker's kernel_heap_mib field (process.memoryUsage().arrayBuffers) reported 0 inside the Worker, so that metric is unusable.
- CHALLENGE 5 (escape and output edge cases the suite skipped): (a) The wrapper's completion value bypasses __finish. 'return box(1,1,1); })()); ((function () { return JSON.stringify([{id:1, name:{...}, color:{evil:[1,2,3]}}]);' returns ok:true with an unvalidated object as color. Handles are still checked on the host (id 0 gives bad-result), so impact is low, but the cap-wrapper-breakout case only 'passes' because globalThis is frozen. (b) Host-side amplification: returning 1500 references to one 2 s shape (131 kernel ops) makes the post-run getVolume/isValid loop run outside the op budget and the guest deadline, and ends as watchdog-killed (2/2, with and without exportStep). (c) harden() misses %RegExpStringIteratorPrototype% and the Shape class and prototype. Symbol.hasInstance and the id getter of Shape can be redefined, so the guest-side Shape checks are cosmetic. The host handle table is the real boundary, and it held.
- CHALLENGE 6 (composition with the OS layer): os-layer.mjs tested --permission only on a plain child, never with the Worker design. Under --permission, new Worker() throws ERR_ACCESS_DENIED unless --allow-worker is passed, and Node then prints 'SecurityWarning: --allow-worker ... could invalidate the permission model'. fs permissions do apply inside the worker. Node documents the permission model as a seat belt, not a boundary against malicious code. The container runs as root, but a uid-65534 process could still run 'unshare -rn' (plain 'unshare -n' was denied), so the 'as on a desktop' row is plausible here. It was not verified on distributions that restrict unprivileged user namespaces (for example Ubuntu 24.04 AppArmor).
- CHALLENGE 7 (legitimate heavy models vs the 5 s watchdog): filleted plates with 36, 100, 196 and 400 holes (cutAll) finished in 0.34-1.3 s, and 24 sequential fuses in 0.5-0.75 s, so typical parts fit. fuseAll of 100 overlapping spheres took 4.0 s, and of 150 or 200 spheres was watchdog-killed. Some plausible organic or lattice models will hit the combined 2 s + 3 s wall budget, because the guest cpuMs and the kernel time share one watchdog.
- SIDE FINDING (DSL, affects Step 1): occt-wasm cut and cutAll return a COMPOUND even when there is one solid. Then fillet throws 'fillet: TopoDS::Solid' (3 of 3 cases). Unwrapping with getSubShapes(s,'solid')[0] first works (fillet ok, valid, volume 71845.26). The guest prelude does not unwrap, so fillet after subtract fails in the current facade.

### Failures and caveats

- The original REPORT.md does not exist, and system rules prevent this subagent from writing .md report files. The '## Independent reproduction' section therefore lives only in this structured output; nothing was appended on disk.
- Correction: the guest CPU deadline (cpuMs 2000 via the interrupt handler) is not a reliable time bound. Polling is driven by bytecode count, so the overshoot is unbounded: measured at 16x (31.8 s for 2 s) on quickjs and 42x (83.9 s) on ng. With the default 3 s grace these become watchdog kills plus respawns.
- Correction: stack-recursion-catch-retry is not a stable 'clean cpu-timeout'. It was watchdog-killed in 8 of 12 targeted runs, and ran 5000.92 ms in the suite rerun against a 5000 ms watchdog.
- Correction: 'Worker stdout capture is how to stop the OCCT STEP writer from corrupting MCP stdio' is incomplete. OcctKernel.init({createModule}) with print/printErr fixes it in-process with 0 leaked bytes. Patching console.log after load does NOT work (448 bytes still leak), because out is bound at load.
- Gap: OCCT kernel memory has no per-run cap. The occt-wasm memory max is 4 GiB, and its high-water mark persists for the worker's lifetime (RSS 128 -> 962 MiB, which stayed). The kernel_heap_mib metric in sandbox-worker.mjs reads 0 inside the Worker and is meaningless.
- Gap: per-part host post-processing (getVolume, isValid, optional exportStep) is not counted in maxOps and not covered by the guest deadline. 1500 returned references to one shape force a watchdog kill.
- Gap: the __finish wrapper can be bypassed through the script completion value ('})()); ((function(){ return "<json>";'). Unvalidated color objects reach the host result. The host handle check still holds.
- Gap: harden() leaves %RegExpStringIteratorPrototype% and the Shape class and prototype unfrozen, so the guest can redefine Symbol.hasInstance and the id getter. The guest-side handle checks are cosmetic; only the host table matters.
- Gap: the Worker design plus node --permission requires --allow-worker, which Node flags with a SecurityWarning. The OS-layer test never combined the two.
- DSL bug surfaced: boolean results are compounds, and fillet then fails with 'fillet: TopoDS::Solid'. The prelude must unwrap single-solid compounds.
- Noise: every timing ran on a shared 4 vCPU box with other agents. My medians for cold start (223 vs 184 ms) and enclosure round trip (110.8 vs 74.8 ms) are higher than the original, but the conclusions do not change.

### Recommendations for Step 1

- Keep the core architecture; the reproduction supports it. One long-lived Worker (8 MB stack) owns occt-wasm. Each run gets a fresh QuickJS 0.32.0 sync instance with a capped WebAssembly.Memory (128 MiB). Only numbers and strings cross the bridge, with a host-side handle table, signature checks, op, batch and handle budgets, and a main-thread wall-clock watchdog with respawn.
- Treat the watchdog as THE CPU bound and the interrupt handler as best-effort only. Pre-spawn a standby worker so a kill costs about 20 ms (terminate) instead of about 200 ms (cold start). Report watchdog kills to the agent as 'timeout' (same error class as cpu-timeout). Do not promise exact guest-time limits.
- Separate the budgets. Use a guest-JS deadline (about 2 s, best-effort), a kernel-time budget accumulated in the bridge (check elapsed host_ms before each op and refuse new ops once over budget), and a larger wall watchdog (for example 15-30 s, configurable) so lattice or organic fuseAll models (100 spheres = 4 s) are not killed while runaway scripts still are.
- Silence OCCT at init with OcctKernel.init({createModule: (o) => factory({...o, print: log, printErr: log})}) and route the text to stderr or the log. Keep Worker stdout:true capture as a second layer. Never rely on patching console.log after load. Add a CI test asserting the MCP server's stdout carries only JSON-RPC frames during STEP export.
- Recycle the kernel worker on a memory high-water mark. Read the OCCT module's HEAP buffer size, or RSS, after each run, and respawn above a threshold (for example 1 GiB) or every N runs, because wasm memory never shrinks. Remove or fix the kernel_heap_mib metric, which reads 0.
- Move result delivery off the eval completion value. Have __finish call a privately captured host capability (or call main via ctx.callFunction from the host), validate name and color types on the host, cap the part count (for example 64), and dedupe repeated handles before the per-part volume, validity and STEP work. Count that work against the kernel budget.
- Extend harden() to the remaining hidden intrinsics (the RegExpStringIterator, %AsyncFromSyncIteratorPrototype% and similar iterator prototypes) and freeze the Shape class and prototype in the prelude. Keep stating in docs that the host handle table, not guest-side checks, is the security boundary.
- Fix the DSL facade: after every boolean, unwrap a single-solid compound with getSubShapes(s,'solid')[0], or have fillet and chamfer do it. Then fillet-after-subtract (the most common CAD idiom) works. Add this as a starter regression test.
- For OS confinement in Step 1, document that node --permission is a seat belt rather than a security boundary, that it needs --allow-worker with the Worker design, and that it does not block network. Use unshare -n or a platform sandbox on Linux only where available. Plan separate macOS and Windows stories rather than assuming unshare.
- Reject node:vm, SES-only and @sebastianwessel/quickjs as the boundary. The reproduction confirms vm escapes, no CPU or memory bound under SES, and default process/fetch/env exposure plus host crashes in 3 of 8 runs for wessel. Pin quickjs-emscripten-core 0.32.0 with the sync variants, and avoid asyncify (dispose aborts reproduced).
