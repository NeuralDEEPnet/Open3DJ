## 1. Vision and positioning

Open3DJ is an open-source, local-first parametric CAD engine and desktop workbench, **built first for AI agents and made trustworthy for professionals**. Agents rarely fail at CAD because they cannot write code; they fail because they cannot see what the code did, cannot point at geometry stably, cannot recover from kernel errors and cannot prove the result is right. Frontier models alone reach only 0.565-0.812 executability on industrial tasks (https://arxiv.org/abs/2609.03773) and the best agentic Parametric CAD Bench V3 score is 61/100 (https://cadbench.ai/), while execution-verified loops with kernel metrics plus renders lift median IoU from 0.81 to 0.96 (CADSmith, https://arxiv.org/html/2603.26512) and clarification cuts invalidity from 4.8% to 0.9% (ProCAD, https://arxiv.org/abs/2602.03045). Open3DJ's product is therefore the feedback loop: native OCCT 8.0.1 in sandboxed workers managed by a local Rust daemon; one typed command contract exposed identically over MCP (every feature works at protocol 2025-06-18, with 2026-07-28 features as add-ons), CLI and SDKs; an evidence-rich GeometryReport on every change; references whose resolution is always reported; branches and proposals reviewed per operation by humans; deterministic replay; and a public benchmark that gates every release. Cloud GPUs, 3dj.app included, are optional providers.

It is the open, installable counterpart to Zoo (proprietary engine, video-streamed viewport; https://github.com/kittycad/modeling-app), Autodesk's Fusion MCP servers (local unauthenticated or session-capped cloud; https://help.autodesk.com/view/fusion360/ENU/?guid=FMCP-OVERVIEW), library-level build123d/text-to-cad skill packs with no persistent editable document, and SolidCraft. SolidCraft is a fast-moving, permissively licensed Rust app that ships on the truck kernel (vendored, Apache-2.0) and is developing a separate, experimental SolidCore SMLib port. It already ships fillets, assemblies and sheet metal (see [research/landscape-ai-cad.md](../landscape-ai-cad.md)). Open3DJ does not compete on feature count. It competes on verification, evidence, references, security and provider breadth.

## 2. What "best agentic CAD" means (measurable goals)

"Best for agents" is a claim we must be able to prove false. Every goal below is measured by `o3dj-bench` in CI and published on a public results page for each release.

| # | Goal | Target at v0.5 public launch | Target at v1.0 |
|---|---|---|---|
| G1 | Agent task success on the o3dj-bench agent suite (create, edit and repair tasks, graded by executable spec assertions plus gates) using Claude Code with a frontier model | ≥ 75% | ≥ 85% |
| G2 | Lift over the best open baseline harness (build123d-mcp, same model, same tasks) | +10 pts success | +15 pts |
| G3 | CADGenBench score | Submitted, with maintainer validation requested, and scoring in the unvalidated table at or above build123d-mcp's best validated score with the same model and effort (currently 0.8298: build123d-mcp 0.3.85 with Claude Opus 5.5 at max effort, 24 Sep 2026). Validated-tier status is reported, not gated | In the maintainer-validated tier: ≥ the best validated score overall at the time of release (currently 0.8298; the top unvalidated score is 0.8482). Reaching this bar at the v0.5 launch is a stretch |
| G4 | Error recovery: share of script or kernel errors fixed by the agent within 2 further calls | ≥ 80% | ≥ 90% |
| G5 | Median tokens per GeometryReport (concise mode) | ≤ 300 | ≤ 250 |
| G6 | Median tool calls per solved "create" task | ≤ 8 | ≤ 6 |
| G7 | Reference stability over a 1,000-edit parameter sweep on the golden corpus | ≥ 95% exact or re-resolved, **0 silent mis-resolutions** | ≥ 98%, 0 silent |
| G8 | Invalid-output rate (BRepCheck invalid or non-watertight output that the report labelled `valid`) | 0 | 0 |
| G9 | Warm `run` on the 18 public 3dj starters, and sandbox overhead per run (week-0 hypotheses H-run and H-sandbox below) | p50 < 1 s, p95 < 2 s; overhead p50 ≤ 50 ms, p95 ≤ 100 ms | p50 < 0.5 s; overhead ≤ 30 ms (re-set after week-0 data) |
| G10 | Install to first agent-built part, in recorded user tests | < 3 min | < 2 min |
| G11 | STEP AP242 round trip on a 150-part corpus, cross-read by FreeCAD and OCP | ≥ 98% pass | ≥ 99.5% |
| G12 | Parity: MCP, CLI, TS and Python SDK schemas identical (CI test) | 100% | 100% |
| G13 | Same-platform deterministic replay of `provenance.jsonl` (hash equality; week-0 hypothesis H-det) | 100% | 100%, plus cross-platform semantic equivalence at tolerances set from the week-0 H-det cross-OS data (this 1.0 target is re-set after week 0; see the Determinism row in section 4) |

**G3 correction.** The earlier "self-reported 0.457" baseline was a real, validated row, but it was GPT-5.5 with build123d-mcp 0.3.59 (27 Jun 2026). build123d-mcp has since reached 0.8298 validated. CADGenBench is Hugging Face's Apache-2.0 benchmark of 81 tasks (49 drawing-to-part, 32 STEP edits); invalid solids score 0. The P3 submission includes a request for maintainer validation. Rows publish as unvalidated, and promotion to the validated tier is a manual methodology review that the Hugging Face maintainers run on their own schedule. So that an outside review cannot block the release, the v0.5 exit needs only the submitted score in the unvalidated table at or above the target, with validation requested; if validation is still pending at launch, the results page says so. The validated tier becomes a gate only at 1.0. Both G3 reference values are re-read from the validated leaderboard at each release. Today they resolve to the same number because build123d-mcp holds the top validated row; they diverge as soon as another harness overtakes it. Source: [research/gap-9.md](../gap-9.md), https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-submissions.

**G13 risk.** OCCT PR #1600 (open, unreviewed) shows `BRepOffset_MakeOffset` iterating maps keyed by pointer hash, so native OCCT 8.0.1 results can differ between processes (one input succeeded in 11 of 20 fresh processes). Plan to carry a deterministic-iteration patch for BRepOffset (or port the fix taucad made for the same bug class in libcascade 3.1.0), or narrow G13. Warm-worker reuse also trades against replay determinism. Source: [research/gap-8.md](../gap-8.md), https://github.com/Open-Cascade-SAS/OCCT/pull/1600.

Release gates use G1, G4, G7, G8, G11, G12 and G13. IoU and Chamfer distance are only reported. They are not gated, because of survivorship bias: they are computed only on samples that executed (https://arxiv.org/html/2605.18430v1).

### Week-0 performance hypotheses

The performance numbers above are hypotheses until the week-0 OCCT benchmark spike measures them. Each is tested with a written protocol on four reference machines: a Windows x64 Iris Xe laptop (16 GB), an M-series Mac, a GitHub Linux x64 runner and an 8 GB floor machine. Raw JSON from each is published. Source: [research/gap-8.md](../gap-8.md).

| ID | Hypothesis | Notes |
|---|---|---|
| H-run | Warm `run` p50 < 1 s and p95 < 2 s on the 18 starters, split by stage (script, kernel, tessellation, report, snapshot) | One native measurement (OCP 8.0.1, 4-vCPU Xeon) gave fuse 3.0 ms, 12-edge fillet 6.9 ms, 40-box fuse 110 ms, 100-hole cut 145 ms, cut plus mesh plus STEP write 311 ms |
| H-sandbox | Sandboxed warm run minus the same run unsandboxed in-process: p50 ≤ 50 ms, p95 ≤ 100 ms. Cold worker spawn ≤ 1.5 s, reported per OS including Windows AppContainer | bubblewrap startup is about 3-9 ms; no published AppContainer figure exists |
| H-mem | Native worker idle RSS ≤ 150 MB, starter p95 peak ≤ 600 MB, recycle at 1 GB, hard cap 1.5 GB; daemon, UI and 2 workers fit on the 8 GB floor; 10,000-op leak soak | WASM field reports show leaks (replicad #282) and heaps of 0.7-3.8 GB (Tau PR #839) |
| H-ratio | Same-machine WASM/native ≤ 2x p50 on the starters before the WASM backend is used for share links or reference mode. Run occt-wasm, libcascade 3.1.0 (as a benchmark comparator only, see the WASM backend row in section 4) and native side by side. It is not a gate for a WASM-backed Agent Preview; section 6 says which goals apply in that case | The only published study (taucad, self-reported, one M2 Pro) shows 1.1-2x on typical ops, 3.16x on a small fuse and parity on a 40-box fuse |
| H-det | Hash equality across 20 fresh processes and 20 warm-worker reuses on each OS, including a shell/offset corpus. The same runs record, per op class, how far topology counts and measures (volume, area, bbox) differ between the OSes; that data sets the cross-platform tolerance tiers in section 4 | Fails today on some offset inputs because of OCCT PR #1600. No research note gives a cross-platform tolerance figure yet |

## 3. Target users

1. **Coding-agent users (primary, from the Agent Preview):** developers and hardware engineers driving Claude Code, Codex, Cursor, Gemini/Antigravity or Goose who want reliable parts unattended or interactively; one-line install.
2. **Agent and tool builders:** teams building CAD agents, evals and fine-tunes who need a sandboxed, deterministic, benchmark-compatible engine. build123d 0.13 runs unmodified in Tier B; CadQuery follows when 2.9.0 is released (section 4).
3. **Maker and print professionals:** DfAM gates, evidence-carrying 3MF and print-quote providers; includes 3dj.app users going local-first.
4. **Professional mechanical designers (review from v0.5, sketching from v0.6):** steer and edit agent proposals in a native feature tree, hand off STEP AP242.
5. **Researchers:** reproducible harness for CADGenBench, CAD-bench and permissive CADBench subsets.

Not targeted before 1.0: BIM/AEC, CAM programmers, simulation analysts, 500+-part assemblies.

## 5. MVP definition

The MVP is **v0.5 "Public Beta"**. It is preceded by **v0.1 "Agent Preview"**, a public headless release for agents only. The honest schedule is a range, not a date: Agent Preview in **weeks 12-16** and Public Beta in **weeks 28-44** (section 6 lists the assumptions and what gets cut first).

### v0.1 Agent Preview (headless, weeks 12-16): in scope

**Distribution and runtime**
- `o3dj` single binary covering daemon, CLI, MCP stdio and loopback Streamable HTTP. Targets Windows x64, macOS universal and Linux x64, plus a headless Linux arm64 CLI/MCP build (dropped to v0.6 if its native build fails in the week-0 spike; section 6).

## 10. Relationship with 3dj.app

3dj.app is the closed, hosted sibling. Open3DJ is the open, local engine the ecosystem adopts. Their written **Open-Core Charter** (published as `CHARTER.md` in week 1) says:

1. **Never charged for:** the kernel, the `.o3j` format, every export format, the local MCP/CLI/SDK surface, or local GPU use. Open3DJ is fully functional without a 3dj account.
2. **3dj.app is one provider among several**, behind the public `Provider` trait and MCP provider profile. Conformance tests apply to it like any other. There is no /ee folder, no closed code in the repo, and no 3dj-only APIs. 3dj.app's provider manifest must declare which generative models it runs and their licences; Tencent territory exclusions (EU, UK, South Korea) apply to hosted services offered to customers in those territories ([research/gap-4.md](../gap-4.md)).
3. **Shared open standards:**
   - **"Open3DJ DSL v1"** is defined by Open3DJ as the published 3dj `dslReference` facade plus the corpus-driven undocumented calls (section 4), with a public conformance suite. Co-stewardship of the specification with the 3dj.app team is a **proposal for the 3dj.app team**, not a plan fact.
   - **Design Evidence Pack v2** is published as an open JSON Schema. It extends v1 (gates and confidence labels measured ±0.15 / observed ±0.35 / inferred ±0.80 / assumed) with gate locations, waivers, provenance heads and STEP/3MF mappings.
4. **Integration points (as 3dj's MCP works today, read 27 Oct 2026; [research/gap-9.md](../gap-9.md)):**
   - `provider:3dj` text-to-3D: on the managed fleet, using 3dj's modelId/poll/download job shape. `get_model_download_url` returns GLB only. `list_providers` serves router health and allowance.
   - `provider:3dj` image-to-3D: `generate_from_image_url` takes only a publicly reachable HTTPS URL (max 12 MB), and no 3dj tool accepts file bytes, base64 or a path. Sending a local image means hosting it publicly, which is egress. Open3DJ therefore requires an explicit per-job egress approval and a host for a short-lived signed URL: either a bucket the user configures (S3, R2 or GCS, with credentials in the OS keychain, paid for by the user under the user's own region and retention settings) or a 3dj presigned-upload endpoint (**proposal for the 3dj.app team**). Neural Deep operates no bucket for Open3DJ. The approval shows the host, the region and the URL expiry before the upload.
   - Print quotes: `request_print_quote` needs the modelId of a completed model saved in the user's 3dj account, and its only free text is `notes` (up to 2,000 characters). It has no field for a file, evidence or hashes, so `o3dj_quote` cannot send Open3DJ parts or evidence packs today. Either 3dj adds an upload tool and an evidence/hash field before v0.5 (**proposal for the 3dj.app team**), or v0.5 3dj quotes are limited as follows. `o3dj_quote` gets an optional `provider_ref` input (for 3dj, a `modelId`) next to `doc_id` and `rev`, so its input is `{action: request|list, doc_id, rev, provider, material, qty, provider_ref?}` on MCP, CLI and both SDKs (G12). In v0.5 a 3dj quote is possible only when both conditions hold:
     - the doc came from a `provider:3dj` generation whose 3dj `modelId` is recorded in the doc's provenance, and the caller passes that `modelId` as `provider_ref`;
     - the requested `rev` is geometrically identical to the imported 3dj asset, meaning its content hash equals the hash recorded at import.

     Open3DJ then sends the `modelId` to 3dj's `request_print_quote` and puts that content hash in `notes`, so the quote and the hash describe the same part. If the doc was edited after import (the main reason to bring it into Open3DJ), 3dj would quote the unedited model while the hash described different geometry, so `o3dj_quote` refuses with the structured error `PROVIDER_CANNOT_RECEIVE_EDITED_PART` and points to the 3dj upload-tool proposal. Any doc without a recorded 3dj `modelId` is also refused with a structured error, because 3dj returns GLB only and accepts no upload, so there is no way to map an arbitrary Open3DJ doc to a 3dj `modelId`. 3dj.app's own instructions say its inspection evidence and file hashes are "operator attestations, not verified"; local evidence would make them verifiable once 3dj can receive it. ARCHITECTURE.md (the `o3dj_quote` schema in section 5.2 and the 3dj gap table in section 7.2) states the same rule ([research/gap-9.md](../gap-9.md)).
   - Later, a hosted relay that lets ChatGPT and claude.ai reach a user's Open3DJ projects (**proposal for the 3dj.app team**).
5. **Convergence (proposal for the 3dj.app team):** 3dj.app's browser workbench could move from its current kernel onto Open3DJ's WASM backend. That kernel is reportedly OpenCascade.js 7.7.2 (from the brief), possibly already OCCT 8.0.1, because the starters use replicad 1.1.0's `cutPlane` and replicad runs only on OCCT 8.0.1 since v1.0.0; it is confirmed with the 3dj.app team in week 0 ([research/gap-2.md](../gap-2.md)). The move is targeted at v0.8, so that 3dj.app dogfoods the open core publicly. This is a commitment the closed product would have to make; it is not assumed by this plan.
6. **Monetisation stays on 3dj.app:** GPU credits with a free allowance, hosted MCP metered as usage, the operator print marketplace (EUR quotes), and an enterprise/on-prem tier. This follows the Ollama and Zoo patterns. Whether this revenue pays for the open core is a founder decision (section 7).

If `facade/` is LGPL-2.1, it lives in a separately licensed directory (or is built as a dynamically linked library) with its own LICENSE file and NOTICE entry. brepjs (vendored or mirrored interfaces) is Apache-2.0. lib3mf is BSD-2 and Manifold is Apache-2.0.
- **Boundary:**
  - GPL and AGPL code (OpenSCAD, slicers, SolveSpace, CGAL algorithm packages, FreeCAD CAM, brepkit-wasm) runs only as subprocess providers in separate repos, or not at all.
  - PlaneGCS (LGPL-2.1+) is dynamically loaded and built from source, avoiding the PyPI SSPL metadata conflict.
  - Restricted-licence model packs (TripoSG, TRELLIS.2, Hunyuan3D, any texturing pack with non-commercial renderers) are opt-in, never default, with manifests that agents can read over MCP.
- **CI licence gate, four layers** ([research/gap-4.md](../gap-4.md)). It fails on GPL, AGPL, Tencent or non-commercial terms entering the core or a default pack:
  1. package metadata (cargo-deny, pip and npm metadata);
  2. LICENSE files of git-installed CUDA extensions;
  3. Hugging Face card `license`/`license_name` for every downloaded weight, including nested configs (for example TRELLIS.2's background-removal model);
  4. in-file licence headers, scanned with ScanCode.
  Pip metadata alone would not catch TripoSG's Tencent terms, which sit in a subfolder LICENSE and a file header.
- **Contribution:** DCO sign-off, no CLA, inbound = outbound.

**Governance**
- `GOVERNANCE.md` sets out a company-led model with module owners (kernel, contract, UI, providers, stdlib, bench) through `CODEOWNERS`.
- Public RFCs follow the Rust template, with a 10-day final comment period that includes at least 5 business days.
- **Neutral-host trigger:** the trademark and donations move to a neutral host (Commonhaus Foundation, or an FPA-style association) when either condition is met:
  - three or more organisations each employ a maintainer with merge rights; or
  - v1.0 ships, whichever comes first.
- **AGENTS.md clean-room rules:** do not read GPL or AGPL CAD source (FreeCAD, SolveSpace, OpenSCAD, QCAD, LibreCAD). OCCT is used through its public API, and no OCCT code is copied into permissively licensed files. 3dj.app's closed code is not used; `lib.*` is re-authored from the public `dslReference`. AI-generated contributions are labelled and reviewed like any other, and the per-work-package AI-use policy in section 7 applies.
- **Culture:** blameless. Exploratory spikes are welcome in `rfcs/experiments/`. Failed experiments are documented, not punished, and the "what we tried" log is part of the docs. Ambitious off-path ideas are invited through RFCs.

**Naming** ([research/gap-5.md](../gap-5.md); not legal advice)
- What the US register shows (27 Oct 2026): **OPEN3D** is a live US registration (Reg. 6468139, class 9, "downloadable computer software for an open-source library ... that deals with 3D data"), owned by a foundation that runs an active trademark programme (it also owns OPENCV). "OPEN3DJ" contains the whole mark plus one letter, for nearly the same goods. Bare **3DJ** has no live US registration in classes 9 or 42. Nobody has filed OPEN3DJ or O3DJ.
- EU and UK registers could not be reached, so EU/UK clearance is open. Known prior users of "3DJ" include 3DJake (an Austrian 3D-printing retailer) and several UK companies named 3DJ. No "2013 3DJ online store" was found; the only 2013 entity is a dissolved UK business-support company.
- All namespaces are currently free: npm `open3dj` and `@open3dj`, PyPI `open3dj`, crates `open3dj` and `o3dj`, GitHub org `open3dj`, and `open3dj.com/.org/.io/.dev/.app`.
- **Founder decision in weeks 0-2, before any package listing, signing certificate or launch.** The options, presented neutrally:
  - keep "Open3DJ", subject to counsel's clearance against OPEN3D; or
  - use a 3DJ house-mark name such as "3DJ Open" or "3DJ Workbench".
  Counsel review is recommended either way, including a full EU/UK search. Filing **3DJ** in classes 9 and 42 (US, EU, UK via Madrid) is an option for the company.
- Namespaces are reserved only under the final name, as real 0.0.x releases (registries disfavour empty placeholders). Until the decision, the project and these documents keep the name Open3DJ.
